<objective>
Close G-06-APPX-02 (code review WR-01; verifier truth 1 warning). APPX-02 says "User can remove a provisioned package", but every row, including Provisioned rows, calls the per-user `RemovePackageAsync`, which never deprovisions. A Provisioned row's "Remove Package" therefore does nothing or fails. Also fold in the cheap part of WR-02 (one unreadable package aborts the whole list), WR-07 and IN-04.

Purpose: removing a provisioned package actually removes it from the provisioned set, and the user is told the system-wide consequence before confirming.
Output: `AppxPackage.PackageFamilyName`, `IAppxPackageService.DeprovisionPackageAsync`, its WinRT implementation, view-model routing, and a scope-stating confirmation.
</objective>

D-02 interpretation (gap scope item 4). D-02 reads: "Appx Manager lists both installed and provisioned packages. Removal via PackageManager.RemovePackageAsync. The real app enumerates/removes provisioned packages." It locks the WinRT PackageManager API family (D-01) and RemovePackageAsync as the removal call, and it states the intent that provisioned packages can be removed. It does NOT lock per-user-only removal. Per-user RemovePackageAsync cannot fulfil that stated intent for a provisioned package:
- Microsoft Learn: `RemovalOptions.RemoveForAllUsers` "Removes a package for all users on the device" and makes no deprovisioning claim.
- `PackageManager.DeprovisionPackageForAllUsersAsync(string packageFamilyName)`, Windows 10 1809+, "Deprovisions an app Package so new users on the device will no longer have the app automatically installed. The caller of this method must have administrator privilege."
So this plan honours D-02 literally for Installed rows (unchanged RemovePackageAsync) and fulfils D-02's stated intent for Provisioned rows with the same PackageManager API family. Recorded assumption: "remove a provisioned package" means deprovision, the same as Remove-AppxProvisionedPackage; copies already installed for existing users are not touched. Research Pitfall 6 predicted exactly this gap.

Twin rows: `RefreshAsync` concatenates installed and provisioned lists, so a package can appear twice. They are kept as two rows on purpose, because each now has a distinct, correct action. Merging them is not needed to close the gap.
</context>
