Locked decisions that bind this plan (CONTEXT.md):
- D-04: QuietUninstallString is preferred over UninstallString; Copy Command copies the raw UninstallString. Both stay unchanged.
- D-05: uninstall runs through a direct `Process.Start` in the view model, with no process-runner abstraction. This plan keeps that and fixes how the command line is handed to `Process.Start`.
- D-10 / D-11 / D-12 / D-13: elevation check, explicit confirmation, user-facing failure messages, and a list reload after the operation.
- D-03: the three uninstall registry hives are untouched.

Decision taken here (Claude's discretion, gap scope item 1): how to split the command line. Options considered:
1. Wrap the command in a command interpreter (`cmd.exe /c <command>`). Rejected. The interpreter expands `&`, `|`, `^` and `%VAR%` inside an elevated, registry-sourced string. HKCU entries are writable by any non-elevated process (IN-01). The review's `ArgumentList` variant also breaks quoted paths, because .NET escapes inner quotes as `\"` and cmd.exe does not unescape them.
2. Split everything with CommandLineToArgvW and re-quote each element. Rejected. MsiExec and NSIS (`_?=`) parse their own raw command line, so re-quoting changes what they receive.
3. Chosen: split off only the executable token, using the CreateProcess rules (a quoted first token, or the shortest space-delimited prefix that names an existing file). Assign the remainder unchanged to `ProcessStartInfo.Arguments`, with shell execution disabled. This is what "it just creates a process" (D-05) means, and it keeps the argument bytes exactly as Windows itself would pass them.

Assumption recorded: research assumption A8 ("shell execution can handle uninstall strings with arguments") was wrong, and the verifier reproduced the failure. This plan supersedes it.
